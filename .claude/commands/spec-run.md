# /spec-run — SPEC 실행·검증·보고

입력: `$ARGUMENTS`

`CLAUDE.md`의 경계·정지 조건·근거 규칙·Git 규칙을 모두 따른다. 단계 순서를 바꾸지 않는다.

## 0. 입력

- 첫 토큰은 SPEC ID(`SPEC_007`) 또는 경로. ID면 `specs/SPEC_007_*.md`.
- `사람확인:` 뒤는 사람이 직접 확인한 결과다. 항목별로 나눈다(`3 OK`, `5 NG: 너무 느림`).
- `[Button pressed: SPEC_NNN <항목> OK|NG|메모] <한 줄>` 형식도 같은 입력이다(`SPEC_NNN 사람확인: <항목> OK`, `<항목> NG: <한 줄>`, `<항목> 메모: <한 줄>`). 원문은 그대로 기록한다.
- `사람확인:`만 있고 구현할 것이 없으면 1단계 뒤 5단계로 간다(회차를 세지 않음).

## 1. 사전 점검 (코드 건드리기 전)

1. SPEC 전체를 읽는다.
2. `사람확인:`이 있으면 항목마다 `log.mjs append confirmations '{"spec":…,"item":…,"result":"OK|NG|MEMO","raw":"<원문>"}'`. 원문은 고치지 않는다. NG는 이번에 고칠 대상이다. 메모는 판정이 아니다: 그 항목은 ⏳로 두고 내용을 보고에 옮기며, 고칠 것이면 이번 대상이다.
3. 확인한다(하나라도 걸리면 6·7단계만 하고 끝):
   - `status`가 `DRAFT`이거나 `[사람 확인 필요:` 가 남아 있음 → 질문을 보고
   - `depends_on` 중 DONE 아닌 것(또는 `after_implemented`인데 IMPLEMENTED도 아닌 것) → `BLOCKED`
   - `iterations` ≥ `max_iterations` → `STOPPED`
   - `log/failures.jsonl`에서 이 SPEC의 시그니처와 「avoid」를 읽어 둔다
4. `iterations`를 1 올리고 `status: IN_PROGRESS`로 바꾼다(이번 회차 = N).

## 2. 계획

만들거나 고칠 파일과 각 파일이 맡을 완료 조건을 짧게 적는다. 이전 실패가 있으면 이번에 무엇을 다르게 할지 한 줄. SPEC에 없는 결정은 CLAUDE.md 5장 결정 등급으로: 되돌리기 쉬우면 가결정하고 진행, 아니면 `BLOCKED`.

## 3. 구현

- SPEC 「파일」에 있는 파일만. 「범위 밖」은 만들지 않는다(미리 만들어 두는 것도).
- 검증 명령(`harness.json`)이 틀려서 고쳐야 하면 고치되 약하게 만들지 않는다(검사 대상을 줄이거나 실패를 숨기지 않음). 보고 「가결정」에 바꾼 전·후를 적는다.
- 공개 이름·문구·수치는 SPEC 글자 그대로.
- 자동 검증을 시험 데이터·러너로 넣는다(7장: 변이 시험·긴 명령). 이전 시험은 지우지 않는다.

## 4. 자동 검증 — 이번 실행에서 돌린 결과만 근거

1. `node .claude/harness/verify.mjs --set regression --json` → 항목별 `ok`·`exit`·`tail`
2. SPEC 「자동 검증」에 적힌 것만 더 돌린다(grep, 스크린샷, 회귀 밖 `harness.json` 항목은 그 `cmd`). 스크린샷은 직접 열어 보고 관찰을 적는다.
3. worktree에서 했다면 1을 그 worktree에서 돌린다(새 worktree 통과 규칙).

실패하면 CLAUDE.md 4장대로 시그니처를 세고 기록한다.
- 이미 1 이상(이번이 2회째) → 고치지 말고 `STOPPED`, 6단계로.
- 처음이면 원인을 고쳐 4단계를 처음부터 한 번 더. 그래도 실패면 기록하고 끝.

## 5. 판정

완료 조건을 한 줄씩: ✅(4단계 출력·`파일:줄`·스크린샷 관찰·confirmations의 OK) / ❌(실패 출력, NG) / ⏳.
상태: ❌ 있음 → `IN_PROGRESS`(정지 조건이면 `STOPPED`) · ❌ 없고 ⏳ 있음 → `IMPLEMENTED` · 전부 ✅ → `DONE`.

## 6. 기록·커밋

- SPEC front matter `status:` 를 판정으로 고치고, 본문 끝 「실행 기록」에 `- <날짜> 회차 N: <상태> — <조건별 근거: 1 ✅ <출력·파일:줄> · 2 ✅ … · 3 ⏳>`. 상세 근거는 여기에 두고 보고에는 옮기지 않는다.
- `log.mjs append runs '{"cmd":"/spec-run","spec":…,"iteration":N,"status":…,"evidence":"<한 줄>"}'`
- `MEMORY.md`: 다음 세션이 알아야 할 것만 고친다(남은 ⏳, 열린 질문, 주의). 실행 로그를 쌓지 않는다.
- **커밋**: CLAUDE.md 6장대로(SPEC·`log/`·`MEMORY.md` 포함). 4단계 뒤 제품 파일을 고치지 않았으면 회귀는 4단계 결과로 갈음한다. `IN_PROGRESS`·`STOPPED`·`BLOCKED`면 세션을 마칠 때 `wip:` 커밋.

## 7. 보고 — 짧게(5줄 안팎)

사람은 대화(폰)로 읽는다. 조건별 근거 표·변경 파일 목록은 보고에 쓰지 않는다(SPEC 「실행 기록」과 커밋에 있음).

```
**SPEC_NNN — <상태>** (회차 N/max) · 커밋 <해시>
- 한 일: <한 줄>
- 결과 예: <생성물이 바뀌었으면 실제 결과 2~3개>          ← 없으면 줄 생략
- ❌ <번호>: <실패 한 줄>                                  ← ❌만, 없으면 줄 생략
- 가결정: <고른 것 · 이유>                                 ← 사람이 알아야 할 것만, 대안은 SPEC에
- ⏳ <번호>: <무엇을 보면 되는지 한 줄>                    ← 한 동작, 없으면 줄 생략
- 다음: <한 줄>
[buttons: SPEC_NNN <항목> OK | SPEC_NNN <항목> NG | SPEC_NNN <항목> 메모]   ← ⏳ 항목마다 한 행(`<항목>` = 완료 조건 번호), ⏳가 없으면 두지 않는다
```

사람이 버튼 대신 글로 답하면 `/spec-run SPEC_NNN 사람확인: <항목> OK` / `<항목> NG: <내용>`으로 처리한다.
